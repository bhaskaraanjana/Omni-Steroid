# Requirements Document

## Introduction

This document defines an evidence-backed, end-to-end assessment of the current repository. The assessment determines what is implemented, what works under fresh local verification, what fails, what remains unverified, and how the product compares with two named capability benchmarks. The assessment changes no production implementation.

## Glossary

- **Repository_State_Assessor**: The system that inventories, verifies, classifies, and reports the current state of the Omni Steroid repository.
- **Repository**: The Omni Steroid workspace at the assessment baseline.
- **Assessment_Baseline**: The recorded commit, branch, working-tree state, operating system, hardware inventory, tool versions, and assessment start time.
- **Production_Code**: Tracked source, test, build, packaging, migration, and runtime-configuration files outside the assessment specification and assessment output locations.
- **Assessment_Artifact**: A report, command log, measurement result, or temporary file created solely by the assessment.
- **Documentary_Claim**: A statement about product behavior, quality, platform support, security, privacy, build status, test status, or release readiness in repository documentation.
- **Material_Claim**: A Documentary_Claim that affects a user-visible capability, safety property, supported platform, quality gate, installation path, or release-readiness conclusion.
- **Fresh_Evidence**: Evidence produced by a command or observation executed against the Assessment_Baseline during the current assessment.
- **Historical_Evidence**: A committed result or prior log produced before the current assessment.
- **Evidence_Record**: A record containing the check identifier, exact command or procedure, start time, duration, exit status, relevant output, environment, source revision, and resulting Assessment_Status.
- **Verification_Plane**: One assessment area: Python_Engine, TypeScript_UI, Rust_Tauri_Shell, Product_Build, Local_E2E, Hardware_Integration, Security_Privacy, or Packaging_Release.
- **Python_Engine**: The Python FastAPI and WebSocket sidecar under `engine/` and the associated pytest suite under `tests/`.
- **TypeScript_UI**: The React and TypeScript frontend under `apps/ui/src/` and the associated Vitest suite.
- **Rust_Tauri_Shell**: The Rust desktop shell under `apps/ui/src-tauri/`, including sidecar supervision and operating-system integration.
- **Product_Build**: A locally produced engine, frontend, desktop, or installer artifact generated by a repository-defined build path.
- **Local_E2E**: A Playwright-driven local end-to-end check using the production frontend build, local Python_Engine, loopback networking, and no live External_Provider request.
- **Hardware_Integration**: A local check that depends on a microphone, system-audio loopback device, graphics processor, local model weights, or operating-system desktop facilities.
- **External_Provider**: A remote AI, speech, voice, email, calendar, contact, or other third-party service reachable outside the local machine.
- **Local_Model**: Model weights stored on the local machine for speech recognition, voice activity detection, or retrieval.
- **Dense_Retrieval_Weights**: The local embedding model files required to exercise the dense tier of hybrid retrieval.
- **STT_Accuracy**: Speech-to-text accuracy measured against labelled local audio by word error rate, with corpus size, audio duration, language, model, and hardware recorded.
- **Capability_Parity_Matrix**: A row-level comparison of Omni Steroid against the Granola_Capability_Set and Wispr_Flow_Capability_Set.
- **Granola_Capability_Set**: The meeting-intelligence benchmark covering bot-free capture, transcription, notes, enhancement, live assistance, meeting recall, integrations, export, privacy, and platform support.
- **Wispr_Flow_Capability_Set**: The dictation benchmark covering global activation, recording modes, transcription, text injection, cleanup, personalization, faithfulness, history, commands, performance, and platform support.
- **Assessment_Status**: Exactly one of Verified_Working, Verified_Partial, Fresh_Failure, Integration_Failed, Not_Implemented, Environment_Blocked, Historical_Only, Unverified, or Not_Applicable.
- **Verified_Working**: Fresh_Evidence demonstrates the complete scoped behavior with a passing result.
- **Verified_Partial**: Fresh_Evidence demonstrates a defined subset and identifies the unverified or failing remainder.
- **Fresh_Failure**: Fresh_Evidence reproduces a non-hardware failure in an available and correctly configured local environment.
- **Integration_Failed**: Fresh_Evidence demonstrates that an available hardware device, driver, model, permission, or operating-system facility fails the scoped Hardware_Integration behavior.
- **Not_Implemented**: Current code and configuration contain no executable path for the scoped behavior.
- **Environment_Blocked**: A named unavailable prerequisite prevents execution without establishing a product defect.
- **Historical_Only**: Historical_Evidence exists, but no Fresh_Evidence establishes the current result.
- **Unverified**: The assessment finds an executable or claimed path but obtains neither Fresh_Evidence nor sufficient evidence for Environment_Blocked.
- **Not_Applicable**: The scoped behavior does not apply to the assessed operating system or repository configuration.
- **Assessment_Report**: The final human-readable assessment containing evidence, classifications, parity matrices, gaps, risks, and prioritized next actions.

## Requirements


### Requirement 1: Establish a Reproducible and Non-Destructive Baseline

**User Story:** As a repository owner, I want the assessment tied to an exact baseline, so that every conclusion is reproducible and existing work remains intact.

#### Acceptance Criteria

1. WHEN an assessment begins, THE Repository_State_Assessor SHALL create an Assessment_Baseline that records the commit identifier, branch name or detached state, staged tracked changes, unstaged tracked changes, untracked paths, operating-system name and version, detected hardware inventory, version of every tool used by the assessment, and assessment start date and time with time-zone offset.
2. WHEN selecting a conclusion for a scoped claim, THE Repository_State_Assessor SHALL apply the following evidence precedence from highest to lowest: Fresh_Evidence for behavior executed during the current assessment; current configuration for enabled or selected behavior not resolved by Fresh_Evidence; current code for executable behavior not resolved by Fresh_Evidence or current configuration; Documentary_Claims; and Historical_Evidence.
3. WHEN two or more evidence sources provide conflicting values for the same scoped claim, THE Repository_State_Assessor SHALL create an Assessment_Artifact containing every conflicting value, the source of each value, each available collection date or an explicit indication that the date is unavailable, the selected conclusion, and the evidence-precedence basis for that conclusion.
4. WHILE an assessment is in progress, THE Repository_State_Assessor SHALL preserve every tracked and untracked workspace path that existed in the Assessment_Baseline without modifying, overwriting, renaming, moving, or deleting the path.
5. WHEN an assessment terminates successfully, fails, or is aborted, THE Repository_State_Assessor SHALL leave the set of Production_Code files, the Production_Code paths, and every Production_Code file byte sequence identical to the Assessment_Baseline.
6. WHILE an assessment is in progress, THE Repository_State_Assessor SHALL restrict every file-system write, including writes produced by executed commands, to Assessment_Artifacts created by the current assessment within designated assessment or temporary output locations.
7. IF a planned assessment operation would create, modify, overwrite, rename, move, or delete Production_Code or pre-existing tracked or untracked workspace content, THEN THE Repository_State_Assessor SHALL omit the planned assessment operation.
8. WHEN the Repository_State_Assessor omits an operation under criterion 7, THE Repository_State_Assessor SHALL create an Assessment_Artifact identifying the omitted command or procedure, the content that would have been affected, the reason for omission, and each dependent check classified as Unverified.
9. WHEN an assessment terminates successfully, fails, or is aborted, THE Repository_State_Assessor SHALL create an Assessment_Artifact that records a final comparison of the Assessment_Baseline against the resulting workspace for pre-existing tracked paths, pre-existing untracked paths, Production_Code byte sequences, and writes outside designated assessment or temporary output locations.

### Requirement 2: Trace Repository Claims to Executable Reality

**User Story:** As a product stakeholder, I want repository claims mapped to implementation and evidence, so that intent is distinguishable from current behavior.

#### Acceptance Criteria

1. THE Repository_State_Assessor SHALL inventory every independently verifiable Material_Claim contained in the primary product overview, feature, architecture, security and privacy, packaging and release, and evidence and results documents present at the Assessment_Baseline, with the exact claim text and source location recorded for each Material_Claim.
2. IF current source or configuration provides an executable path for a Material_Claim, THEN THE Repository_State_Assessor SHALL link the Material_Claim to every located source location, configuration declaration, and test case that directly implements, enables, disables, or verifies the claimed behavior, with absent configuration or test links identified as absent.
3. IF a search of all Production_Code finds no executable path for a Material_Claim, THEN THE Repository_State_Assessor SHALL leave the implementation links empty and cite search evidence that records the exact search terms or procedures, searched scope, inspected matches, and conclusion that no qualifying implementation was found.
4. IF a search satisfying criterion 3 finds no executable path for a Material_Claim, THEN THE Repository_State_Assessor SHALL assign Not_Implemented to the Material_Claim.
5. IF prior measurements are the only evidence supporting a Material_Claim at completion of the current assessment, THEN THE Repository_State_Assessor SHALL assign Historical_Only to the Material_Claim and cite each available measurement date or mark the date unknown.
6. IF a Documentary_Claim predates and disagrees with newer current code, current configuration, or Fresh_Evidence for the same scope, THEN THE Repository_State_Assessor SHALL classify the Documentary_Claim as stale and cite both the Documentary_Claim and the newer evidence.
7. IF two or more Documentary_Claims applicable to the Assessment_Baseline assert mutually exclusive values or behaviors for the same scope, THEN THE Repository_State_Assessor SHALL classify each affected Documentary_Claim as contradictory, cite every conflicting source, and identify the conclusion selected under the evidence-precedence rules.
8. IF a Documentary_Claim explicitly describes a capability, quality level, platform, build state, test state, or release state as planned, proposed, targeted, future, or incomplete rather than currently available, THEN THE Repository_State_Assessor SHALL classify the Documentary_Claim as aspirational and cite the wording that establishes the classification.
9. IF a Documentary_Claim asserts current behavior but has no linked executable path, Fresh_Evidence, or Historical_Evidence, THEN THE Repository_State_Assessor SHALL classify the Documentary_Claim as unsupported and cite the evidence established by the search required in criterion 3.
10. THE Repository_State_Assessor SHALL include separate claim-traceability entries for the documented target of 90 percent line coverage and the documented target of 85 percent branch coverage, with each entry distinguishing the target, current configuration scope, Documentary_Claim sources, Historical_Evidence, and Fresh_Evidence measurement.

### Requirement 3: Execute Fresh Language and Build Verification

**User Story:** As an engineer, I want fresh verification across every implementation language and build path, so that cached or historical success is not presented as current success.

#### Acceptance Criteria

1. WHEN a verification command is selected, THE Repository_State_Assessor SHALL execute the repository-defined invocation against the Assessment_Baseline during the current assessment as a newly started, terminating non-watch process rather than reuse an earlier process, cached result, or Historical_Evidence.
2. WHEN Python_Engine verification begins, THE Repository_State_Assessor SHALL execute the repository-defined lint verification as a terminating non-watch process.
3. WHEN Python_Engine verification begins, THE Repository_State_Assessor SHALL execute the repository-defined strict type verification as a terminating non-watch process.
4. WHEN Python_Engine test verification begins, THE Repository_State_Assessor SHALL execute the repository-defined pytest suite as a terminating non-watch process with hardware-dependent tests and live External_Provider requests excluded.
5. WHEN Python_Engine coverage verification begins, THE Repository_State_Assessor SHALL produce fresh line-coverage and branch-coverage percentages and record separately whether the measured values meet the documented targets of 90 percent line coverage and 85 percent branch coverage.
6. WHEN TypeScript_UI verification begins, THE Repository_State_Assessor SHALL execute the repository-defined TypeScript type verification as a terminating non-watch process.
7. WHEN TypeScript_UI test verification begins, THE Repository_State_Assessor SHALL execute the repository-defined Vitest suite once with watch mode disabled.
8. WHEN TypeScript_UI coverage verification begins, THE Repository_State_Assessor SHALL produce fresh statement-coverage, line-coverage, branch-coverage, and function-coverage percentages as four separate measurements.
9. WHEN Rust_Tauri_Shell verification begins, THE Repository_State_Assessor SHALL execute repository-defined Rust compile checking and every Rust test discovered at the Assessment_Baseline, including every discovered integration test, as terminating non-watch processes.
10. WHEN Product_Build verification begins, THE Repository_State_Assessor SHALL execute the repository-defined build paths for the Python_Engine package, production frontend, and every host-supported desktop target defined by the current repository configuration and evaluate the component results as one aggregate Product_Build gate.
11. IF one or more required Product_Build components return a non-passing result, THEN THE Repository_State_Assessor SHALL assign Fresh_Failure to the aggregate Product_Build gate and retain a separate result for each required component.
12. IF the current repository contains no executable verification or build path for a required check, THEN THE Repository_State_Assessor SHALL assign Not_Implemented to that check and record the repository search evidence without assigning Environment_Blocked.
13. IF a named toolchain or dependency is confirmed unavailable and prevents a verification command from executing the scoped checks, THEN THE Repository_State_Assessor SHALL assign Environment_Blocked, record the unavailable prerequisite and detection evidence, record the minimum rerun procedure, and exclude the check from product-failure totals.
14. IF a verification command executes the scoped checks after all named prerequisites are confirmed available and returns a nonzero exit status for a non-hardware failure, THEN THE Repository_State_Assessor SHALL assign Fresh_Failure and retain the observed failure output.
15. WHEN a verification command terminates or is classified Environment_Blocked before execution, THE Repository_State_Assessor SHALL create one Evidence_Record containing every field defined in the Glossary for the command or attempted command.
16. WHEN a verification command reports warnings or test outcomes, THE Repository_State_Assessor SHALL report warning details and separate exact counts for passed, failed, skipped, deselected, and ignored tests without including any skipped, deselected, or ignored test in the passing-test count.
17. THE Repository_State_Assessor SHALL perform all Requirement 3 verification without creating, changing, moving, or deleting any Production_Code file.


### Requirement 4: Verify Local End-to-End Behavior

**User Story:** As a user, I want the real local application path exercised end to end, so that isolated unit success is not mistaken for product success.

#### Acceptance Criteria

1. WHERE the production frontend build is available, the local Python_Engine can start, a Playwright-configured browser can launch, required local test data and local services are available, and required loopback ports can be bound, THE Repository_State_Assessor SHALL execute every Local_E2E scenario present in the current repository Playwright test sources that requires only local resources and is included by current repository configuration.
2. WHEN a Local_E2E scenario executes, THE Repository_State_Assessor SHALL launch the production frontend build and the local Python_Engine through repository-defined production local startup paths without substituting a frontend development server, mocked application shell, or test-only engine.
3. WHEN a Local_E2E scenario executes, THE Repository_State_Assessor SHALL drive a Playwright-configured browser executable rather than a mocked browser or mocked page.
4. WHILE Local_E2E is running, THE Repository_State_Assessor SHALL restrict every network connection initiated by the Local_E2E scenarios, production frontend, local Python_Engine, and browser to a loopback network interface.
5. THE Repository_State_Assessor SHALL assign exactly one disposition to every Local_E2E scenario present in the current repository Playwright test sources: External_Provider-dependent when the scenario requires a live External_Provider; excluded by repository configuration when current repository configuration prevents execution; Environment_Blocked when a named local prerequisite is unavailable before execution; or executed when all named local prerequisites are available and browser execution is attempted.
6. WHEN an executed Local_E2E scenario fails, THE Repository_State_Assessor SHALL preserve in an Evidence_Record the scenario name, observed failure output, scenario output, production-frontend output, Python_Engine output, browser output, path of every generated screenshot or trace, and an explicit statement when no screenshot or trace was generated.
7. WHEN Local_E2E starts one or more local processes, THE Repository_State_Assessor SHALL terminate every process created by the current assessment after Local_E2E completes or aborts.
8. WHEN Local_E2E terminates processes created by the current assessment, THE Repository_State_Assessor SHALL preserve every pre-existing process without stopping or restarting the pre-existing process.
9. IF a Local_E2E scenario requires a live External_Provider, THEN THE Repository_State_Assessor SHALL omit scenario execution, assign the External_Provider-dependent disposition, and exclude the scenario from executed-scenario and local-product-failure totals.
10. WHILE Local_E2E is running, THE Repository_State_Assessor SHALL restrict the count of live External_Provider requests to zero.

### Requirement 5: Verify Hardware, Models, and Operating-System Integration

**User Story:** As a desktop user, I want hardware-dependent and native behaviors checked on the available machine, so that simulated coverage is distinguishable from real integration evidence.

#### Acceptance Criteria

1. WHEN microphone hardware and microphone permission are confirmed available before execution, THE Repository_State_Assessor SHALL create an Evidence_Record demonstrating discovery of the selected microphone, capture start within 10 seconds of the start request, receipt within 10 seconds of at least one captured frame containing at least one non-zero audio sample from non-private test audio, capture stop within 5 seconds of the stop request, and resource release by reopening and stopping the same microphone within 5 seconds.
2. WHEN system-audio loopback hardware is confirmed available before execution, THE Repository_State_Assessor SHALL create an Evidence_Record demonstrating discovery of the selected loopback device, capture start within 10 seconds of the start request, generation of non-private local audio, receipt during the generation interval of at least one captured frame containing at least one non-zero audio sample, identification of the captured stream as system-audio loopback rather than microphone input, capture stop within 5 seconds of the stop request, and resource release by reopening and stopping the same loopback device within 5 seconds.
3. WHEN a graphics processor and a Local_Model are confirmed available before execution, THE Repository_State_Assessor SHALL create an Evidence_Record demonstrating Local_Model loading within 300 seconds, completion of exactly one local inference within 300 seconds, production of a non-empty inference result, identification of the compute device selected for the inference, and inference duration measured in milliseconds.
4. WHEN Dense_Retrieval_Weights are confirmed available before execution, THE Repository_State_Assessor SHALL create an Evidence_Record demonstrating generation of one non-empty dense embedding within 120 seconds and completion within 120 seconds of one retrieval whose recorded result identifies participation by the dense tier.
5. IF Dense_Retrieval_Weights are absent before execution, THEN THE Repository_State_Assessor SHALL assign Environment_Blocked to the dense-retrieval check, identify the absent weights as the unavailable prerequisite, execute one retrieval using the documented fallback tier, and record the fallback result and Assessment_Status separately.
6. WHEN a labelled local speech corpus and a speech Local_Model are confirmed available before execution, THE Repository_State_Assessor SHALL create an Evidence_Record containing the measured STT_Accuracy as uncapped word error rate, corpus item count, total audio duration, language, speech Local_Model, hardware, and an explicit indication that a measured value of 0.0 percent is valid.
7. IF either the labelled local speech corpus or the speech Local_Model is absent before execution, THEN THE Repository_State_Assessor SHALL assign Environment_Blocked to STT_Accuracy, identify each absent prerequisite, and omit a computed STT_Accuracy value.
8. WHEN the host operating-system facilities required for Tauri launch and Python_Engine sidecar operation are confirmed available before execution, THE Repository_State_Assessor SHALL create an Evidence_Record demonstrating Tauri launch within 60 seconds, Python_Engine sidecar start within 30 seconds of Tauri launch, sidecar availability while Tauri is running, sidecar stop within 10 seconds of Tauri exit, and absence of an assessment-created sidecar process after that interval.
9. IF every prerequisite for a Hardware_Integration check was confirmed available before execution and an executed check fails to produce a required outcome within the specified time bound, terminates unexpectedly, or reports a runtime malfunction, THEN THE Repository_State_Assessor SHALL assign Integration_Failed and create an Evidence_Record that identifies the confirmed prerequisite, executed procedure, failed outcome, and observed malfunction.
10. IF a permission, device, driver, model, or host operating-system facility required by a Hardware_Integration check cannot be confirmed available before any scoped behavior executes, THEN THE Repository_State_Assessor SHALL assign Environment_Blocked and create an Evidence_Record that identifies the unavailable prerequisite, detection evidence, absence of a product-failure conclusion, and minimum procedure required to make the prerequisite available and rerun the check.
11. THE Repository_State_Assessor SHALL report microphone capture, system-audio loopback capture, graphics-processor selection, Local_Model inference, dense retrieval, STT_Accuracy, Tauri launch, Python_Engine sidecar lifecycle, tray behavior, global hotkey handling, and supported text injection as separate Hardware_Integration checks, each with exactly one Assessment_Status and one Evidence_Record reference.
12. WHEN the host operating-system facilities required for configured tray behavior are confirmed available before execution, THE Repository_State_Assessor SHALL create an Evidence_Record demonstrating tray presence within 30 seconds of Tauri launch and the observable configured outcome of each discovered tray action within 10 seconds of invoking the action.
13. WHEN the host operating-system facilities required for the configured global hotkey are confirmed available before execution, THE Repository_State_Assessor SHALL create an Evidence_Record demonstrating registration of the configured hotkey and exactly one configured application response within 5 seconds of one hotkey activation while the application lacks input focus.
14. WHEN the host operating-system facilities required for supported text injection are confirmed available before execution, THE Repository_State_Assessor SHALL create an Evidence_Record demonstrating insertion of one non-private test string exactly once and without character changes into a disposable local target within 5 seconds of one injection request.

### Requirement 6: Produce an Explicit Granola and Wispr Flow Parity Matrix

**User Story:** As a product decision-maker, I want explicit competitor-oriented capability matrices, so that product completeness is evaluated against recognizable meeting and dictation workflows.

#### Acceptance Criteria

1. THE Repository_State_Assessor SHALL include one Granola_Capability_Set row for each of the following capabilities: bot-free meeting capture, live transcription, user-authored notes, enhanced notes, live assistance, meeting library, meeting search, meeting chat, calendar integration, auto-detection, export, privacy, and platform support.
2. THE Repository_State_Assessor SHALL include one Wispr_Flow_Capability_Set row for each of the following capabilities: global activation, push-to-talk, locked recording, speech transcription, cross-application text injection, cleanup styles, personal dictionary, raw-text retention, faithfulness protection, dictation history, history search, note mode, command mode, latency, accuracy, and platform support.
3. THE Capability_Parity_Matrix SHALL contain separate columns for benchmark capability, benchmark source, benchmark source date, Omni Documentary_Claim, implementation location, Fresh_Evidence reference, Assessment_Status, limitation, and parity conclusion.
4. WHERE a benchmark source has a publication or last-updated date no later than the Assessment_Baseline start time and no more than 365 calendar days before the Assessment_Baseline start time, and the source is available in the Repository or through research permitted for the current assessment, THE Repository_State_Assessor SHALL record the most recent qualifying source and source date for each supported benchmark row.
5. IF a benchmark row lacks a source satisfying criterion 4 without competitor web research permitted for the current assessment, THEN THE Repository_State_Assessor SHALL mark the benchmark basis Unverified and record the missing or non-current source basis as the limitation.
6. IF a benchmark row has an Unverified benchmark basis, THEN THE Repository_State_Assessor SHALL continue the repository assessment by evaluating the Omni Documentary_Claim, implementation location, Fresh_Evidence, and Assessment_Status independently of the unavailable benchmark evidence.
7. WHEN Fresh_Evidence verifies at least one but fewer than all behaviors represented by a benchmark row, THE Repository_State_Assessor SHALL assign Verified_Partial and identify the exact supported subset and the unverified or failing remainder in the limitation.
8. WHEN a benchmark row addresses feature quality, latency, accuracy, reliability, or platform breadth, THE Capability_Parity_Matrix SHALL present the feature-presence Assessment_Status separately from each measurement result, measurement unit, assessed scope, and Fresh_Evidence reference.
9. IF Fresh_Evidence does not measure a quality, latency, accuracy, reliability, or platform-breadth dimension associated with a benchmark row, THEN THE Repository_State_Assessor SHALL identify the dimension as Unverified without inferring the dimension from feature presence.
10. WHEN assigning an Omni parity conclusion, THE Repository_State_Assessor SHALL derive the conclusion from the associated Evidence_Record without treating similarity between Omni and benchmark feature names as evidence of parity.


### Requirement 7: Assess Security and Privacy Without Live Provider Calls

**User Story:** As a security-conscious owner, I want local-first and approval guarantees assessed without data egress, so that verification does not violate the properties under review.

#### Acceptance Criteria

1. WHEN the Repository_State_Assessor verifies an External_Provider path, THE Repository_State_Assessor SHALL use only static inspection or hermetic execution with synthetic non-private inputs, repository-controlled mocks or local fakes, no real provider credentials, and no network communication beyond local loopback.
2. THE Repository_State_Assessor SHALL restrict the count of live calls and transmitted payloads to AI, speech, voice, email, calendar, contact, and other External_Providers to zero during every assessment activity.
3. WHEN security and privacy controls are assessed, THE Repository_State_Assessor SHALL create a separate Evidence_Record for each of the following controls: local-only storage of audio, transcripts, embeddings, notes, and keys; zero transmission of analytics, usage data, crash reports, or other telemetry; key custody that prevents plaintext persistence, log disclosure, or UI-process disclosure; kill-switch blocking of every external call while local capture, transcription, and vault behavior remains available; approval-before-execute for calendar events, contact upserts, vault writes, and drafts; Gmail draft creation without mail-send capability; rejection of modification or deletion of existing append-only audit entries while permitting new entries; and preservation of user-authored content outside managed vault regions.
4. WHEN a security or privacy control is assessed, THE Repository_State_Assessor SHALL record yes or no for each applicable verification property: hermetic, meaning all runtime inputs and mutable dependencies were locally controlled and networking did not exceed local loopback; mocked, meaning a repository-controlled substitute represented an external dependency; local-loopback, meaning all network communication remained on the assessed machine; hardware-backed, meaning the check used local hardware-backed custody; and static-only, meaning no product code was executed.
5. WHEN the Repository_State_Assessor creates or updates an Assessment_Artifact, THE Repository_State_Assessor SHALL omit private audio and replace every secret value, credential, private transcript excerpt, and identifying personal-file name, path, or content with a non-sensitive category label before the Assessment_Artifact is persisted.
6. WHEN a security control test completes successfully against the Assessment_Baseline and covers the complete scoped control, THE Repository_State_Assessor SHALL assign Verified_Working from the Fresh_Evidence regardless of the date or result of Historical_Evidence.
7. IF a security control has current code and tests but no test execution during the current assessment, THEN THE Repository_State_Assessor SHALL assign Environment_Blocked only when an Evidence_Record identifies a specific unavailable local prerequisite and detection evidence, and SHALL assign Unverified otherwise.
8. WHEN an external-call path is assessed dynamically, THE Repository_State_Assessor SHALL invoke the path using absent credentials or a repository-controlled local fake configured to reject the operation.
9. WHEN an external-call path is invoked under a refusal condition, THE Repository_State_Assessor SHALL verify that zero requests reach a non-loopback address and zero External_Provider side effects occur.
10. WHEN an external-call path is invoked under a refusal condition, THE Repository_State_Assessor SHALL verify that the caller receives an observable failure indication, no pending action is marked executed, and no pre-existing user data is created, modified, or deleted.
11. IF an Assessment_Artifact contains an unredacted secret, credential, private audio, private transcript, or identifying personal-file data, THEN THE Repository_State_Assessor SHALL withhold the Assessment_Artifact from the Assessment_Report until the sensitive value or content is omitted or replaced with a non-sensitive category label.

### Requirement 8: Apply an Evidence-Based Status Taxonomy

**User Story:** As a reviewer, I want consistent classifications, so that failures, missing features, historical claims, and machine limitations cannot be conflated.

#### Acceptance Criteria

1. THE Repository_State_Assessor SHALL assign exactly one primary Assessment_Status to each claim, verification check, and parity row without assigning a second Assessment_Status as a concurrent primary status for the same scope.
2. WHEN Fresh_Evidence demonstrates a passing result for every required behavior in the exact assessed scope, THE Repository_State_Assessor SHALL assign Verified_Working and reference the passing Fresh_Evidence.
3. WHEN Fresh_Evidence demonstrates a defined subset but not all required behaviors in a scope that is not an aggregate gate requiring failure when any component fails, THE Repository_State_Assessor SHALL assign Verified_Partial and identify the exact verified subset.
4. IF a non-Hardware_Integration scope executes in an available and correctly configured local environment and either no required scoped behavior passes or an aggregate gate fails under the defined component-failure rule, THEN THE Repository_State_Assessor SHALL assign Fresh_Failure supported by an Evidence_Record containing a reproducible command or procedure and the observed failure signature.
5. IF an executed Hardware_Integration check fails because a required hardware device, driver, model, permission, or operating-system facility that was confirmed available before execution malfunctions, THEN THE Repository_State_Assessor SHALL assign Integration_Failed supported by an Evidence_Record identifying the available prerequisite and observed malfunction.
6. IF a named prerequisite is confirmed unavailable before the dependent check can execute, THEN THE Repository_State_Assessor SHALL assign Environment_Blocked supported by an Evidence_Record identifying the unavailable prerequisite, evidence of unavailability, and minimum rerun procedure, and exclude the check from product-failure totals.
7. IF Historical_Evidence exists for an applicable scope with a current executable or claimed path, no Fresh_Evidence establishes a current passing or failing result, and no unavailable prerequisite supports Environment_Blocked, THEN THE Repository_State_Assessor SHALL assign Historical_Only and identify the Historical_Evidence date or mark the date as unknown.
8. IF an applicable scope has a current executable or claimed path but has no Fresh_Evidence, no Historical_Evidence, and insufficient evidence for Environment_Blocked, THEN THE Repository_State_Assessor SHALL assign Unverified and report the check separately from Verified_Working, Fresh_Failure, Integration_Failed, and Environment_Blocked totals.
9. WHEN generating status totals in the Assessment_Report, THE Repository_State_Assessor SHALL calculate each total from row-level primary Assessment_Status values, count each row exactly once, and make the sum of the status totals equal the number of classified rows in the same report scope.
10. WHEN Verified_Partial is assigned to a claim, verification check, or parity row, THE Repository_State_Assessor SHALL enumerate every remaining subset, assign exactly one primary Assessment_Status to each separately scoped subset, and refrain from treating a subset status as an additional primary status of the parent scope.
11. IF an applicable scoped behavior has no executable path in current code and configuration after a documented repository search, THEN THE Repository_State_Assessor SHALL assign Not_Implemented regardless of Documentary_Claims or Historical_Evidence and cite the search evidence.
12. IF a scoped behavior does not apply to the assessed operating system or repository configuration, THEN THE Repository_State_Assessor SHALL assign Not_Applicable and record the operating-system or configuration basis for the classification.

### Requirement 9: Deliver an Actionable Repository State Report

**User Story:** As a repository owner, I want a concise but complete state report, so that I can decide what to fix, validate, or defer next.

#### Acceptance Criteria

1. THE Assessment_Report SHALL include a summary containing the row-level total for each Assessment_Status and a grand total equal to the number of reported claim, verification-check, and parity-row classifications.
2.
